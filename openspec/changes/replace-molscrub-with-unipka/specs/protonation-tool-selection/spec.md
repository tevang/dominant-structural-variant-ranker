## Purpose

Selects which tool performs the protomer-generation stage and defines availability, provenance, and failure behavior for each selectable tool.

## ADDED Requirements

### Requirement: Protomer generation tool dispatch

The workflow SHALL select the protomer-generation implementation from the `protonation.tool` configuration value, supporting `unipka` and `molscrub`, with `unipka` as the default for new configurations.

#### Scenario: Default runs use Uni-Pka

- **WHEN** a `prepare-ligands` run executes with default configuration
- **THEN** protomers are generated by Uni-Pka and no molscrub installation is required

#### Scenario: Molscrub remains selectable

- **WHEN** a run configures `protonation.tool: molscrub`
- **THEN** protomers are generated by molscrub with the previously existing candidate-generation and plausibility-selection behavior

#### Scenario: Unknown tool name

- **WHEN** a run configures `protonation.tool` to an unsupported value
- **THEN** configuration validation rejects the value before the run starts

### Requirement: Per-tool availability checks

`dsvr doctor` SHALL report availability of each selectable protonation tool: for Uni-Pka the configured container runtime and image, for molscrub the Python module or CLI. The default workflow SHALL treat a missing Uni-Pka container/image as a required-tool failure and molscrub as optional.

#### Scenario: Missing Uni-Pka image

- **WHEN** `dsvr doctor` runs while the configured Uni-Pka image or `.sif` path does not exist
- **THEN** doctor reports the Uni-Pka check as failed with an install/acquisition hint naming the Zenodo `unipka.sif` and the EasyDock build recipe

#### Scenario: Selected tool unavailable at run time

- **WHEN** a run starts with a `protonation.tool` whose required runtime is missing
- **THEN** the run fails at the protonation stage with an error naming the tool and how to install it, without silently falling back to another tool

### Requirement: Protonation provenance records the selected tool

Every protomer record SHALL record the protonation tool and the exact invocation (command or call description) that produced it in its provenance fields.

#### Scenario: Uni-Pka provenance

- **WHEN** Uni-Pka produces a protomer
- **THEN** the record's `source_software` identifies Uni-Pka and `source_command` records the container invocation

### Requirement: Protonation stage reports the active tool

The workflow step listing and run report SHALL name the protonation tool actually used by the run.

#### Scenario: Step metadata follows config

- **WHEN** a run is planned with `protonation.tool: unipka`
- **THEN** the protonation step description and required-tool list reference Uni-Pka rather than molscrub
